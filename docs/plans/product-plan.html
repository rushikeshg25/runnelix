01 / Product boundary

Start with dependable internal automation.

The first release should let a teammate connect a trigger to a few actions, publish the workflow, and diagnose a failed run without reading server logs. Its foundation must survive restarts and support new integration nodes without changes to the execution engine.

“Extensible” means source-code extensibility. A developer adds a node module, its schemas, examples, and tests to this repository. The application ships that node in its next release. There is no external plugin installation, public marketplace, or user-uploaded executable code.

First production release

  • Manual, authenticated webhook, and scheduled triggers.
  • HTTP request, field mapping, condition, merge, bounded iteration, and durable wait nodes.
  • GitHub issue and Slack message integrations. Initial tests use fixture providers.
  • Drafts, immutable published versions, run history, retries, cancellation, and failure diagnosis.
  • OIDC login, workspace roles, encrypted credentials, audit records, quotas, backup, and restore.
  • Versioned workflow JSON import/export, excluding secrets.

Later, when needed

  • Hosted SaaS billing and customer isolation.
  • Public node marketplace and untrusted code execution.
  • Arbitrary JavaScript/Python nodes and unrestricted graph cycles.
  • Collaborative editing, AI workflow generation, and hundreds of connectors.
  • Large-file processing, streaming records, and reusable subworkflows.
  • Human approval workflows and connector-specific polling triggers.

First useful workflow: receive a signed webhook → validate and map fields → select a branch → call an approved HTTP endpoint → inspect the result. Use a controlled mock endpoint first; connect a real service after the execution contract works.

02 / System shape

Separate control flow from integration code.

Use a modular Go backend with separate API and orchestration processes from one repository. TypeScript workers execute integration actions. React renders the editor. Keep deployment boundaries small and module ownership explicit.

Why propose Temporal?

Durable waits, retries, cancellation, and recovery are central product requirements. Temporal supplies those mechanisms; we still own graph semantics, node behavior, credentials, and the user experience. It adds another system to operate and introduces replay/versioning rules.

The simpler infrastructure alternative is a PostgreSQL job table with leases and FOR UPDATE SKIP LOCKED. That reduces deployed components but makes us responsible for lease fencing, timer recovery, retry state, cancellation races, and execution history. Do not assume fewer services means less engineering.

Decision gate: spend the first week proving Go-to-TypeScript activity calls, crash recovery, long waits, worker upgrades, and a self-hosted restore. Keep Temporal if this passes and its operating cost fits. If it fails the budget or maintenance constraint, explicitly narrow the initial semantics before selecting a PostgreSQL runner. Do not implement two engines or a general engine-abstraction framework.

03 / The extension seam

Adding an action should be a local change.

A node type is a versioned definition plus an executor. A workflow contains configured instances of node types. Keep these concepts separate so two HTTP nodes can have different settings while using the same implementation.

// Illustrative contract; finalize exact types in phase 1.
defineNode({
  type: "github.createIssue",
  version: 1,
  title: "Create GitHub issue",
  configSchema, inputSchema, outputSchema,
  credentialType: "github",
  effects: "external-write",
  retrySafety: "reconcile-before-retry",
  async execute(context, input, config) {
    // Context provides scoped credentials, HTTP, cancellation,
    // redacted logging, and a stable logical-action key.
    return createIssue(context, input, config);
  }
});

The example describes a policy, not a claim that GitHub guarantees an idempotent create operation. Each connector must document what it can safely deduplicate or reconcile.

ContractRequired content
DefinitionStable type ID, version, title, category, description, named input/output ports, config/input/output JSON Schemas, field UI hints, examples, and credential type.
Execution contextWorkspace/run/node/invocation IDs, logical-action key, deadline, cancellation, credential accessor, approved HTTP client, logger, and payload references.
ResultSchema-validated output or a typed failure: invalid input, authentication, rate limit, transient, permanent, or uncertain external outcome.
Operational policyTimeout limits, retry safety, concurrency/rate-limit scope, redacted fields, and connector-specific error classification.
VersioningExact implementation version and contract version. Optional explicit draft migration; no silent rewrite of published workflows.

The developer workflow

  1. Add nodes/service/action/ with definition, executor, fixtures, and documentation.
  2. Use the shared SDK for HTTP, credential lookup, cancellation, timeouts, and structured errors.
  3. Add one registration to the internal catalog. The build exports a serializable manifest for Go and the UI; Go never imports TypeScript code.
  4. Run schema tests, success/error fixtures, cancellation tests, and duplicate-delivery tests.
  5. The editor discovers the manifest and renders a form from schemas. Add a custom field widget only when existing widgets cannot express the configuration.
  6. Ship the worker and catalog together. Publish only when a compatible worker deployment supports every pinned node version.

Maintainability acceptance test: add a second integration using only its node module, catalog registration, tests, and docs. No engine or editor changes should be necessary for an ordinary action.

Control nodes are different. A new API action uses the extension seam. A new loop, join policy, or trigger lifecycle changes scheduling semantics and may require compiler and engine work. Treating all of these as arbitrary executable nodes would hide important behavior.

Retain old node implementations while published versions or active runs reference them. Breaking behavior creates a new node version. Worker routing must keep old tasks on compatible deployments; prove this in the first spike. Never route a pinned old run to the latest implementation by accident.

04 / Execution contract

Define the rules before building the canvas.

At publication, the Go compiler validates the graph and produces an immutable execution plan. A run pins the workflow version, node versions, plan version, and interpreter compatibility version. Editing a draft does not change an active run.

  • Graph: a directed acyclic graph. Reject dangling edges, unknown ports, incompatible required inputs, unreachable nodes, and accidental cycles.
  • Data: one JSON value per node invocation. Lists remain values until an explicit Map node expands them. Use named input ports; never infer joins by completion timing.
  • Branches: selected edges carry data; unselected edges carry a skip marker. A join waits for all expected edge outcomes, merges active inputs deterministically, and skips when every input is skipped.
  • Parallel work: bounded per run and workspace. Preserve declared output order, regardless of completion order.
  • Iteration: explicit bounded Map with stable item identities and a defined empty-list result. Start with 1,000 items and concurrency 10 as configurable, benchmarked ceilings. Chunk work or use child executions before history limits are approached.
  • Expressions: evaluate through a limited Go helper. Enforce cost and output-size limits. Record the resulting branch decision or payload reference; do not use wall-clock reads, randomness, or external calls inside replayed orchestration logic.
  • Errors: fail the run by default. An explicit error edge may handle a typed failure. Never silently replace a failed action with an empty success.
  • Wait: persist a timer and release the worker. Cap initial waits at 30 days; retain compatible workers and referenced data for the active run's full lifetime.
  • Cancellation: stop scheduling new nodes and request cancellation of active work. An external request may already have succeeded; cancellation cannot undo it.
  • Retry: bounded exponential backoff with jitter, honoring provider retry instructions. A transient error permits retry only when the action's side-effect policy also permits it.

Manual reruns create a new run with a link to the original and an explicit warning about repeated side effects. Within one run, retries reuse the same logical-action key. Defer arbitrary “resume from this node” until data dependencies and duplicate-action behavior are fully specified.

Trigger rules

Persist a validated webhook and start request in one database transaction before returning 202 Accepted. Deduplicate with a provider event ID or caller idempotency key scoped to the workflow and source. A webhook without a stable event ID cannot be reliably deduplicated from payload similarity alone.

Schedules need an explicit timezone, daylight-saving behavior, overlap policy, and missed-occurrence policy. Default to no overlap and coalescing missed occurrences to one catch-up run. Use one scheduler owner: reconcile application schedule records into Temporal schedules through an outbox, and record the observed schedule revision. Schedule occurrences pass through idempotent admission before the main run starts. Admission reserves an active-run slot to enforce main-run overlap policy; the short-lived schedule wrapper cannot enforce that policy by itself. Do not also run an independent cron loop.

Webhook runs return asynchronously in v1. Synchronous response nodes, external resume signals, and polling triggers can be added later with explicit timeout, authentication, and cursor contracts.

05 / Failure model

A retry can repeat an external action.

Execution delivery is at least once. If an external service accepts a request and the worker crashes before recording success, recovery cannot infer the outcome from a missing local result. An idempotency key works only when the provider supports and enforces it.

For non-idempotent writes, disable automatic retries where an outcome can be ambiguous, including worker-loss retries. Persist an intent record and return structured uncertainty where possible. A local “already done” table cannot close the crash window between a remote commit and a local commit.

06 / Persistence and contracts

Keep sources of truth explicit.

PostgreSQL owns definitions and accepted requests. Temporal owns live orchestration state. PostgreSQL run summaries are query projections, not a second scheduler. Immutable input/output payload references keep sensitive or large values out of orchestration history where possible.

RecordsImportant invariants
workspaces, users, membershipsWorkspace scope on every authorization path; role changes are audited.
workflows, drafts, workflow_versionsOptimistic draft revision; immutable published definition and compiled plan; atomic active-version pointer.
trigger_inbox, start_outbox, schedulesUnique source/event key; transactional acceptance; stable run ID; schedule revision and dispatch status.
runs, node_invocations, attempts, run_eventsSeparate logical invocation from retry attempts. Idempotent event IDs and ordering/checkpoints prevent projection regression.
credentials, credential_versionsCiphertext and key version; workspace ownership; scoped access and explicit rotation/revocation policy.
payloads, node_catalog, audit_eventsSchema/version references; size limits and expiry; immutable audit entries; no plaintext secrets in catalog or audit.

Use foreign keys, uniqueness constraints, and indexes for workspace/run time, pending outbox work, and expiring payloads. All timestamps are stored in UTC; preserve the schedule's IANA timezone separately. A workflow version uses credential references rather than embedding credential values.

Persist immutable attempt outputs before reporting activity completion. Select the canonical invocation result with an idempotent conditional update, so a late worker cannot overwrite an accepted result. Store projection updates as separate idempotent work. Reconcile stale runs against the execution runtime, and persist final summaries before execution history expires. An unavailable projection should appear as stale, not as a false success.

Initial payload policy: small JSON payloads in PostgreSQL, with a proposed 256 KiB limit per node input/output and 1 MiB webhook request limit. Enforce aggregate bytes and invocation count per run too. Retain completed-run payloads for 7 days and summaries for 30 days; active-run dependencies override expiry. Add an S3-compatible store when files or measured storage pressure require it.

07 / User experience

The editor must explain what will run.

  • Workflow list: active version, trigger status, last run, owner, and failure count.
  • Canvas: searchable node picker, explicit ports, selection, keyboard deletion, undo/redo, and clear invalid-edge feedback.
  • Node configuration: schema-generated controls, credential selector, required-field errors, example input, and a preview of mapped values.
  • Mapping: choose an upstream field or enter a bounded expression. Explain missing fields and type mismatches before publication.
  • Publish: show validation errors, version changes, and unresolved credentials. Draft saving and publication are different actions.
  • Test: use sample inputs and mocks by default. Label real external actions clearly; a “test node” can still send a message or create a record.
  • Run inspector: show each invocation's state, attempt count, start/end time, selected branch, sanitized inputs/outputs, and actionable error details.
  • Recovery: distinguish retry scheduled, cancelled, failed, and needs attention. Show when a rerun may repeat writes.

Keep run data separate from the editable draft. View execution against the exact published version. Reconnect SSE from the last event cursor, with a full-state refresh if the cursor has expired.

Desktop is the primary editing surface. On narrow screens, prioritize run inspection, errors, and configuration forms; provide a node-list view so essential actions do not depend on dragging tiny canvas handles. Verify focus order, accessible form labels, keyboard navigation, and zoom.

08 / Trust and access

Internal deployment still needs real boundaries.

Integrate the team's OIDC provider. Use workspace roles: owner, editor, operator, and viewer. Separate editing from production execution privileges, and decide who may use each credential. Enforce permissions on the backend, including payload downloads and SSE streams.

  • Credentials: use envelope encryption with versioned keys held outside the application database. For self-hosting, mount the root key as an operator-managed secret or use an existing KMS. Document backup and recovery of the key separately.
  • Worker access: authenticate internal workers. The credential service checks workspace, run, node type, and credential grants; caller-supplied IDs alone are not authorization.
  • Secret handling: fetch values at execution time. Keep them out of workflow JSON, Temporal arguments/results, logs, exceptions, UI previews, and exports. Redaction is defense in depth, not permission to log raw objects.
  • OAuth: use state/PKCE where applicable, protected callbacks, minimal scopes, and serialized refresh with version checks. Revocation must affect future attempts.
  • Network: block cloud metadata, loopback, and private ranges by default for generic HTTP nodes. Internal integrations require explicit host/network allowlists. Validate resolved destinations and redirects; apply egress controls against DNS rebinding.
  • Webhook abuse: signatures, timestamp/replay windows, request limits, per-trigger quotas, and durable deduplication.
  • Resource abuse: per-run time/step/byte limits, bounded fan-out, workspace concurrency, and credential-scoped rate limits across worker replicas.
  • Audit: record publication, credential changes, role changes, execution/rerun/cancel actions, and policy changes without copying sensitive payloads.

Trusted node modules are code-reviewed and shipped in locked container builds. A TypeScript process is not a security sandbox. Do not add runtime package installation, uploaded scripts, or a code node under the assumption that the existing worker safely isolates them.

09 / Operability and economics

Production readiness needs a failure budget.

Start with Compose for development and a documented single-host pilot. This has a host-level failure domain. A production installation must choose whether restore-based recovery is acceptable or whether replicated application processes and highly available PostgreSQL/Temporal are required. Do not advertise high availability from a single VM.

RPO measures possible data loss during disaster recovery, not routine process failure. Restoring to an earlier time can also make previously completed external effects appear unfinished. The restore runbook must reconcile these before allowing unsafe automatic retries.

Keep infrastructure tied to evidence

  • Temporal: justified by durable multi-step execution. Alternative: PostgreSQL runner with reduced semantics. Revisit if the initial operations spike fails its budget.
  • Redis: defer. Start with PostgreSQL-backed quota/concurrency coordination at modest scale. Add Redis only if measured contention prevents the dispatch target and query/index improvements are insufficient.
  • Object storage: defer for bounded JSON. Add when binary nodes are required or payload storage prevents meeting the restore target.
  • Kubernetes: use only if the team already operates it or multi-host scheduling and independent scaling justify its operating cost. Compose or existing container hosting is the default.
  • Kafka and microservices: no current requirement. Measure queue lag, database contention, and ownership constraints before introducing them.

At 10,000 runs/day × 10 actions/run, plan for 3 million action invocations/month. At an illustrative 8 KiB of total stored input/output per action, raw payloads add about 0.82 GB/day; 7-day retention is about 5.7 GB. At 10× usage, those figures become 8.2 GB/day and 57 GB. Indexes, metadata, Temporal history, replicas, and backups are additional. Long-running pinned payloads can exceed the retention estimate.

Size active worker slots from peak action arrival rate × observed action duration, then account for branching and provider limits. More workers do not overcome an external API quota. Budget roughly 2–4 operator hours/week after stabilization as a planning assumption, then measure it.

Operational checklist

  • TLS, non-root images, health/readiness checks, graceful worker draining, and resource limits.
  • Structured logs and traces with workspace/run/node/attempt IDs; no raw payload logging.
  • Alerts on oldest outbox entry, dispatch lag, failed/uncertain runs, projection lag, worker availability, database disk, and backup age.
  • Versioned SQL migrations with an expand/contract rollout; application rollback only while schema compatibility is preserved.
  • Separate application and Temporal database credentials/databases. A pilot may share a PostgreSQL cluster, but then shares its failure and capacity limits.
  • Documented backup, restore, credential rotation, upgrade, rollback, provider outage, and queue-drain procedures.

Overbuild verdict: build the simple deployment first, with a proven durable runtime. Proposed product outcome: three teammates use five real workflows each week for two consecutive weeks by 31 January 2027. This date assumes work starts by early November; revise it with staffing.

Pause criteria: no real weekly adoption by that date; operations exceed 4 hours/week for four weeks; or the priced deployment exceeds the agreed budget. No spend ceiling has been supplied, so set it before provisioning paid resources. On pause, preserve exports, encrypted backups and keys, local Compose instructions, benchmarks, and a demo. Stop compute without deleting durable state.

10 / Delivery sequence

Build in slices with observable exit gates.

Estimate 14–22 engineer-weeks for this bounded first release, with substantial uncertainty around Temporal operations, connector behavior, and editor polish. Two experienced developers may overlap UI and backend work, but a dependable pilot still needs calendar time for real usage and restore drills. This is not an n8n feature-parity estimate.

0 · Prove the runtime boundary / 1–2 engineer-weeks

Agree on first workflows and operating budget. Run a Go workflow that executes a TypeScript action, waits, retries safely, and survives restarts. Test cross-language serialization and worker version routing. Exercise a basic backup/restore.

Exit: a recorded failure demonstration, supported-version matrix, and explicit Temporal go/no-go decision. No polished canvas yet.

1 · Define contracts and persistence / 2–3 engineer-weeks

Create the repository structure, migrations, CI, OpenAPI, node schemas, task envelopes, workspace authorization, draft/publication model, inbox/outbox, and immutable plan compiler. Build the node test harness and a mock action.

Exit: publish validated workflow JSON, reject invalid graphs, accept a run durably, and demonstrate duplicate trigger handling.

2 · Ship the first complete workflow / 2–3 engineer-weeks

Add a minimal canvas, schema forms, manual/webhook trigger, HTTP action, field mapping, condition, and run inspector. Implement payload access, credentials, typed errors, SSE, and cancellation.

Exit: a teammate builds and runs the example end to end, sees the exact version and mapped values, and diagnoses an intentional failure.

3 · Finish execution semantics / 2–3 engineer-weeks

Add bounded Map, deterministic merge/skip handling, durable waits, schedules, quotas, rate limits, retry policies, uncertainty handling, and idempotent projections. Verify upgrades while runs are active.

Exit: pass the crash matrix, schedule/DST tests, branch and iteration tests, and load envelope.

4 · Prove node extensibility / 2–3 engineer-weeks

Add two real integrations through the internal node contract. Complete OAuth/API-key flows as required, mocked provider tests, version migration examples, docs, and import/export.

Exit: a developer who did not write the engine adds a normal integration node without editing engine or canvas logic. Set a target of one working day for a simple API-key action, excluding provider access delays.

5 · Harden deployment and recovery / 3–5 engineer-weeks

Finish OIDC/role audits, secret and egress checks, retention, metrics, deployment images, upgrade/rollback docs, restore drills, and dependency/license review. Complete desktop/narrow-screen and keyboard QA.

Exit: meet every production release gate below on the actual target environment.

6 · Run a controlled pilot / 2–3 engineer-weeks

Move five useful internal workflows into service. Record failures, support effort, and actual usage. Refine unclear errors and node authoring friction. Add only features required by the pilot.

Exit: two weeks of observed use, reviewed incidents, named operational ownership, and a deliberate release decision.

Dependency order: runtime decision → shared contracts → full workflow → complete semantics → extensibility proof → production gates → pilot. UI work can overlap after the contracts stabilize.

11 / Definition of production-ready

Release against evidence.

These are planned checks, not completed tests. Keep results, environment, and versions with the release record.

  • Correctness: compiler and interpreter tests cover invalid graphs, skip propagation, joins, empty lists, deterministic ordering, limits, and cancellation races.
  • Boundary contracts: Go and TypeScript pass the same JSON fixtures, including structured errors and schema mismatches.
  • Durability: kill API, dispatcher, worker, and runtime connections at each persistence boundary. Accepted work remains recoverable; unsafe external outcomes become visible.
  • Idempotency: duplicate webhook deliveries and duplicate starts produce one intended run. Supported provider actions deduplicate; unsupported actions are not claimed to be exactly once.
  • Version safety: publish v2 and deploy new workers while a v1 run waits. The v1 run resumes with compatible behavior.
  • Authorization: cross-workspace read/write attempts fail for workflows, credentials, runs, payloads, and SSE.
  • Secret safety: sentinel secrets never appear in logs, run history, error serialization, exports, or UI previews.
  • Egress: blocked metadata/private destinations, redirects, and rebinding cases are tested; approved internal targets still work.
  • Operations: backup restoration and upgrade rollback meet the agreed RPO/RTO. Recovery reconciles potentially repeated external effects.
  • Capacity: measure p95 dispatch latency, queue age, memory, database contention, and recovery at the stated workload. Report results rather than extrapolating from a unit test.
  • Usability: a teammate creates, publishes, runs, and diagnoses the example without developer assistance.
  • Extensibility: the second real integration requires no core engine or editor changes.

Use Go unit/race tests, TypeScript tests, JSON-schema fixtures, integration tests with real PostgreSQL and Temporal, controlled mock provider endpoints, and browser end-to-end tests. Inject failures around actual transaction and network boundaries. Keep real-provider smoke tests opt-in and isolated from production accounts.
