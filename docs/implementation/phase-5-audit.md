# Phase 5: transactional audit records

Privileged workspace changes now append an audit record in the same PostgreSQL transaction as the change. If the audit insert fails, the change rolls back. The audit trail records committed product actions, not a best-effort copy of HTTP responses.

Apply migrations through `go run ./cmd/runnelix migrate`, including `012_audit.sql`, before starting this version. Existing objects are not backfilled: records begin with changes made after this migration and code are deployed. The migration does not change existing workflow or credential formats.

## Recorded actions

| Action | Target | Selected change fields |
| --- | --- | --- |
| `workflow.created` / `workflow.imported` | Workflow ID | Initial revision |
| `workflow.draft_saved` | Workflow ID | Saved revision |
| `workflow.published` | Workflow ID | Version ID and draft revision; publication also sets the active version |
| `credential.created` / `credential.rotated` / `credential.revoked` | Credential ID | No credential contents |
| `credential.granted` | Credential ID | Workflow ID; includes grants created during import |
| `membership.provisioned` / `membership.set` | Hash of member issuer/subject | Role, previous role when present, and stored grant flags |
| `membership.removed` | Hash of member issuer/subject | Previous role |
| `run.admitted` | Run ID | Workflow/version IDs, admission or execution mode, manual/webhook/schedule source |
| `run.cancel_requested` | Run ID | Workflow ID |
| `run.resolved` | Invocation ID | Run ID and confirm/fail decision |
| `schedule.saved` | Schedule ID | Workflow ID, desired revision, and enabled flag |

A run admission is not proof of execution or completion. A saved schedule records desired state, not confirmation that Temporal has applied it. Runtime attempts and projection events remain in their existing stores. Reconciliation notes and outputs remain under the existing run-data controls and are not copied to audit records.

Publication, admission, credential grant/revocation, cancellation, and identical reconciliation retries do not create duplicate audit changes. Explicit membership PUTs and credential rotations remain recorded operations; draft and schedule saves create new revisions. Failed validation, denied requests, and rolled-back changes create no success record.

## Actor and data boundaries

Every record contains its workspace-local sequence, actor, target ID, action, database timestamp, request ID, and typed change fields. The API derives the actor from the verified bearer or cookie principal. `oidc:` plus SHA-256 of the JSON principal (`issuer`, then `subject`) matches the existing reconciliation actor format. Membership targets use the same hash. Hashes are stable pseudonymous identifiers, not proof of anonymity.

The API's request ID is generated by the server; a client `X-Request-ID` header cannot replace it. Unauthenticated local development requests are explicitly attributed to `local-development`. The owner-provisioning CLI uses `installation-operator`. Background store operations, including scheduled admissions, default to `system` with no HTTP request ID. Trusted programmatic callers can use `store.WithAuditContext`; it is not an API field.

Audit details have a fixed Go struct. They do not capture names, email addresses, raw subjects, credential values/ciphertext/keys, provider destinations, workflow graphs, payloads, trigger inputs, idempotency keys, session tokens, free-text notes, or provider responses. No generic request-body or metadata-map logging is used. Database constraints bound the action vocabulary, identifiers, sequence range, and metadata size.

## Read the audit trail

In OIDC mode, only workspace owners can call:

```text
GET /v1/workspaces/{workspace}/audit-records?after=0
```

The response is an array of at most 100 records ordered by `sequence`. Pass the last returned sequence as `after` to fetch the next page. An omitted cursor means zero; negative, malformed, or JavaScript-unsafe integer cursors return 400. Another workspace's owner receives 403. The endpoint supports the same bearer or browser-session authentication as other workspace routes. Development mode retains its explicitly unauthenticated loopback behavior.

Each workspace has a transactional counter. Appending takes its counter lock until commit. A later record cannot commit with a higher sequence while a lower sequence remains uncommitted, so advancing a cursor does not skip late commits. Rollback also rolls back counter allocation. Use sequence order rather than wall-clock time for pagination. Concurrent audit commits in one workspace serialize briefly; production throughput has not been benchmarked.

## Append-only protection and limits

A database trigger rejects ordinary UPDATE, DELETE, and TRUNCATE statements against `audit_records`, including statements issued by the application table owner. There is no HTTP mutation endpoint or application cleanup path for these records. The app writes audit entries explicitly at the store transaction boundary; generic business-row triggers do not inspect potentially sensitive data.

Audit tables intentionally have no foreign keys to business objects. This avoids new parent-lock ordering conflicts and lets the history outlive business-data retention. Their workspace scope is established by the successful mutation and checked again by the owner-only read endpoint. Direct administrative SQL can bypass the application write path and is outside this audit coverage.

This is not a tamper-proof or externally anchored ledger. A database owner or superuser can disable/drop triggers, alter counters, insert forged rows, or replace backups. Separate runtime database privileges, external archival, and an authorized audit-retention process remain operational work. No audit deletion/retention mechanism ships in this slice. Future terminal-data retention must leave this audit history intact unless a separate audited retention policy is approved.

Login/logout, failed access attempts, provider credential reads, runtime attempts, direct SQL, and deployment/environment configuration edits are not included in this workspace mutation trail. Authentication/security-event logging and production acceptance remain separate work; this slice does not claim the complete security release gate.
